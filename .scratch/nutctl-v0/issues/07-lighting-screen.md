# 07: Lighting screen

**What to build:** Both halves of lighting are configurable in the TUI: the ambient Lighting Effect and Per-Key RGB highlights.

**Blocked by:** 05

**Status:** resolved

- [x] The Lighting Effect is editable: mode, primary/secondary colors, brightness 1–6, speed 1–6, direction
- [x] Per-Key RGB is editable as a slot grid with per-slot colors
- [x] Edits go through the pending/apply/revert mechanics with read-back verification
- [x] Brightness and speed are constrained to the Model's advertised ranges

## Comments

**2026-10-05 — implemented (resolved).** On `main`, next to tickets 01–06.

- **Both halves are one screen with a half toggle** (`internal/tui/lighting.go`): `space` switches the Lighting Effect form ↔ the Per-Key RGB grid in place (the Keys screen's Layer toggle's twin). The form is the ticket's six rows — mode, primary/secondary colors, brightness, speed, direction — with the Settings screen's row cursor and ←/→ editors; the grid is the 128 Per-Key RGB entries (CONTEXT.md) in four columns, windowed like the Keys table, one cursor moved by arrows/pgup/pgdn, `enter` opening the color editor for the selected entry. `*` marks every row and cell that differs from the Device — the same truth the pending line states.
- **Value domains come from the Model's capability set, not literals** (`device.Model.Lighting`, the ticket's "constrained to the Model's advertised ranges"): brightness/speed ranges and the effect-mode offering, extracted from the vendor config `3141-34828-NUT87.ts` (`lightingConfig: {customEffect:[23,24,25], minBrightness:1, maxBrightness:6, minSpeed:1, maxSpeed:6}`) — the same "data observed, not a guess" precedent as `Model.ReportRates`. The editors clamp (`stepUint8`) and cycle (`stepValue`, the Report Rate stepper generalized) inside them; an out-of-domain read is shown as read and steps in at an end.
- **The effect-mode table is bundle data** (`internal/protocol/lighting.json` + `lightingmodes.go`, the Key Action catalog's precedent): the vendor's own `defalutLightingModeList` + `appendLightingModeList`, **fetched 2026-10-05 from the vendor CDN** (`decoded/lighting-C48tIL8G.js` — a lazy chunk the HAR corpus does not carry; provenance in `decoded/README.md`, semantics in `docs/protocol.md` §4). The selection rule is the bundle's own (`useProtocol` in `layout-classic-DSv6_q0d.js`): the default table plus the appended entries the Model's `customEffect` selects, sorted by `sort` → the NUT87 offers 1..19, 23 Rainbow Windmill, 24 Colorful gathering, 25 Neon shadows and 128 Custom. Names are the bundle locale's (`lighting_iconN`); one spelling (`protocol.LightingModeText`) serves the form, the diffs and `nutctl get lighting`.
- **The fetched chunks closed the open semantics** (`decoded/lightingPane-DBmdx-GA.js`, the vendor's own Lighting Edit pane): `colorMode` is 0 = monochrome / 1 = RGB (its two-option radio); `direction` is the arrow its own buttons write — 0 right, 1 left, 2 up, 3 down — and each mode animates ONE pair (`directionPosition:"left"` modes use 0/1, the single `"top"` mode 10 uses 2/3); mode 128 is the Per-Key RGB mode (the chunk's `CUSTOM_LIGHTING_MODE`); mode 0 = backlight off (its lighting switch writes it); and Per-Key RGB entry *i* IS Key Slot *i* (its key-group paint handler writes `customLedData[key.value]`), so the grid names entries from the layout table. `docs/protocol.md` §4 records all of it and corrects the old "custom effects `[23,24,25]`" line (they are the NUT87's three APPENDED modes, not its custom one).
- **A field the effect mode ignores is marked, never rewritten**: the mode table's `isShowSpeed`/`isShowDirection`/`isShowColor` are the vendor's own claims about what the effect animates; those rows render `— not used by this mode` (the Custom mode's color rows point at the Per-Key half) instead of being hidden or silently adjusted.
- **Colors edit through one editor** (opened from the form's color rows and from any grid cell): red/green/blue channels — type the value, or step ±1 / ±16 — and `enter` lands the color in the edit buffer, named the same in the form, the grid, the status bar and the pending line; `esc` changes nothing.
- **Edits ride the shared edit mechanics of ticket 05** (edit.go/write.go): the pending line names them (`lighting mode: 11 Flowing with the Waves → 12 Turning Peaks`, `per-key RGB entry 5 (F5): #000000 → #ff0000`), `a` writes **only the edited block** (a Lighting Effect edit sends SET_LED_EFFECT and never SET_CUSTOM_LED_DATA, and the reverse) through the write gate and read-back verification, `r` reverts with no wire traffic. The SET wire encoding is pinned byte-for-byte: the 16-byte effect block with its forced markers (driverSetting `0xFF`, check code `0xAA 0x55`) and every untouched field keeping the Device's bytes, and the 512-byte Per-Key block with `ledId = entry index`, an untouched entry, and the Device's block-tail marker round-tripped.
- **Testing (both agreed seams):** `internal/tui/lighting_test.go` drives whole sessions with key messages against the fake Device — golden frames (the effect form, the slot grid, the color editor) plus wire assertions (payload bytes, only the edited block out, no wire for edits/revert) and the acceptance's range constraint pinned at both ends; `internal/protocol/lightingmodes_test.go` pins the extraction at the protocol seam (the NUT87's offering written out of the bundle — not recomputed — the direction pairs, the text spellings; same domain-function precedent as `RunChecks`/`Identify`).
