# 04: TUI shell + Device screen

**What to build:** The TUI becomes the front door (ADR-0004): bare `nutctl` opens a tabbed interface where the Device introduces itself and State Files are explicitly saved and loaded. Read-only states and errors are visible, never silent.

**Blocked by:** 03

**Status:** resolved

- [x] Bare `nutctl` opens the TUI; the four screens are navigable with `1`–`4` and `tab`
- [x] The Device screen shows connection state, Device Identity, firmware version, Report Rate, and charge/battery status
- [x] The Device screen offers explicit Save and Load actions; no file is ever written without a user action
- [x] The write-gate prompt and read-only banner follow ADR-0003; a bootloader Device shows a clear read-only state
- [x] Permission failures show an actionable udev hint; device-busy and wrong-Model failures are clearly worded
- [x] TUI behavior is tested through the fake Device with golden rendered frames (the second test seam)

## Comments

**2026-10-05 — implemented (resolved).** On `main`, next to tickets 01–03.

- `internal/tui` (new, ADR-0004: bubbletea + bubbles textinput + lipgloss): `tui.Run` opens the Device and runs the program; `tui.New` makes ONE checked full read pass (the session startup every UI shares) and a Device that cannot be opened or read becomes an error screen showing the error and its hint the whole time — never a silent exit. The shell renders header, tab bar (active screen bracketed so the frame says which one it is without color), screen body, status bar and help line; `1`–`4` jump, `tab`/`shift+tab` cycle, `q`/`ctrl+c` quit. The Keys/Lighting/Settings screens are honest placeholders — their edit mechanics are tickets 05–07; this ticket owns the shell and the Device screen. The Device screen shows connection state, Device Identity, firmware version + status, Report Rate and battery/charge status (the `nutctl info` spellings), and the two State File actions.
- **State File actions (ADR-0005):** `s`/`l` open a path prompt (bubbles textinput, static caret) and nothing is read or written until the user types a path and presses enter — the tests pin that the file does not exist while the prompt is open. Save writes the golden-read format (one code path with `nutctl save`). Load is the write path and runs the CLI's gate verbatim: wrong-Model refusal (still worded by `StateFile.Check`), firmware mismatch warns and proceeds (shown in the notice lines), then before the session's FIRST write a fresh checked read of the Device (ADR-0003's check half — not the startup snapshot), then the golden-read prompt `save current state to ./golden-<ts>.json? [Y/n]` (shared wording `device.GoldenPrompt`; `y` saves the golden and loads, `n` loads without saving — the dismissible escape hatch of spec user story 5 —, `esc` cancels and writes nothing). The apply is `Session.ApplyVerified`: batched writes + read-back verification diff (capped on screen), and the Device's read-back becomes the state on screen.
- **Read-only is a visible state (ADR-0003):** a banner says why the session is read-only — bootloader/firmware-recovery (`firmwareStatus == 1`) or failed self-checks — with every `self-check failed: …` line under it, the Load action is marked refused and pressing `l` names the reason, while Save (a read) stays available. The check failures from the write gate's fresh read land in the same banner.
- **Shared pieces moved to their natural homes** so the CLI and TUI spell things once: `device.Session` (Select/Open/OpenInfo + the full read pass + `ReadChecked`, the write gate's check half), `device.ApplyVerified`/`StateDiffs`/`DiffHeader`, `device.StateFileFor`/`GoldenName`/`GoldenPrompt`, `hid.Hint`/`UdevHint`/`BusyHint` (actionable errors, one spelling for every UI), `protocol.KeyActionText`/`FirmwareStatusText`/`HexRGB`. `internal/cli` now runs through the same session layer (externally unchanged — its whole suite passes untouched).
- **Testing (the second seam):** `internal/tui/tui_test.go` drives whole sessions with key messages against the fake Device (committed fixtures), executing each command synchronously, and asserts golden rendered frames (ANSI-stripped): the Device screen, placeholder screens, the read-only banners (self-check failure with its failure line, bootloader), the Save prompt, the write-gate prompt (pinned clock `Deps.Now` makes `golden-20261005-193000.json` golden-testable), and the permission/busy/wrong-Model error screens. Wire- and file-level assertions cover the rest: no file before enter, the golden read on `y` and none on `n`/`esc`, SET commands only where a write is legal (bootloader, failed self-checks, wrong-Model file and cancelled loads send none), the firmware-mismatch warning, and the write gate refusing a Device that fails its self-checks at gate time. `internal/cli` pins the wiring: bare `nutctl` runs the real program against the fake and exits 0 on `q` (paced input, frames asserted as substrings — the golden frames live in `internal/tui`).
- **Key decisions:** (1) the golden read and the self-check gate rest on a fresh checked read taken when the session's first write is about to happen, not the startup snapshot — the TUI's gate is the CLI's gate, not a weaker cousin; (2) one action at a time: while a command runs off the event loop the keyboard waits (`busy`, ctrl+c still quits) and commands take the Session/state by value, so one goroutine owns the wire and the event loop stays the only Model writer (spec, Session model); (3) the write-gate question is the same string in the CLI and the TUI (`device.GoldenPrompt`), because a gate prompt is policy wording, not UI decoration.

**Code review (two-axis, post-implementation):** fixed the Spec findings — the golden read/check half was the startup snapshot rather than a fresh pre-write read (now `freshReadCmd`, with a test that a Device failing its self-checks at gate time is never written), overlapping apply commands and off-event-loop reads of the Model (the `busy` guard + by-value command arguments), the multi-device error naming `--device` to a TUI user (now also says "or unplug the others"), and the untested firmware-mismatch warning (now golden-adjacent tested); and the Standards finding of the duplicated load write path (`Session.ApplyVerified`, shared `DiffHeader`/`GoldenPrompt`). **Suppressed findings (deliberate):** `TestQuit` asserting the model's Quit message (that is the model's output contract — its exit code — and the program-level exit is separately pinned by `TestBareOpensTheTUI`); the usage-page candidate filter living in `device` rather than `hid` (it is device-identification knowledge, where `Select` already lives); `shift+tab` cycling backwards (two lines beyond the letter of the acceptance, standard tab UX); the three small `switch`-on-mode sites and the `deviceState` view type in the CLI (a four-state mode does not want polymorphism; `deviceState` pairs Model with State for the printers); `Deps.Now` as a clock seam (golden frames need a pinned clock — still asserted as frames and files only); the compare-loop shape in `device/diff.go` (moved code, deliberately unchanged); `tui.New` doing the startup read (documented on the constructor); stale "connected" state after an unplug (hotplug/reconnect is Phase 6 / ticket 08).
