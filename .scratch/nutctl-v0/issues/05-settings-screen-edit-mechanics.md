# 05: Settings screen + edit mechanics

**What to build:** Settings become editable in the TUI with a trustworthy apply loop: edit locally, see what is pending, apply with verification, or revert from the Device. These edit mechanics are shared by every later edit screen.

**Blocked by:** 04

**Status:** resolved

- [x] The Settings screen edits Report Rate (1K/4K/8K), key delay, sleep, and the Fn switch
- [x] The status bar shows pending changes whenever local state differs from the Device
- [x] `a` applies the pending changes with read-back verification; `r` reverts from the Device's actual state
- [x] An applied Report Rate uses the correct wire encoding (1K/4K/8K) and reads back as set
- [x] Unsaved changes are never silently written, and never silently lost when switching screens

## Comments

**2026-10-05 — implemented (resolved).** On `main`, next to tickets 01–04.

- **The edit mechanics are one shared module, not a screen** (the ticket's "shared by every later edit screen"): `internal/tui/edit.go` owns the session's ONE local edit buffer (`Model.local`, a `device.State` beside the Device's actual `Model.state`), the status bar's `pending:` line (`device.StateDiffs(Device → edits)`, capped at 3 with `· and N more`), `a` → `startApply` and `r` → `revert`. Edits belong to the session: switching screens never drops them (pinned by `TestSettingsEditsSurviveScreenSwitch`), and the same `a`/`r` work from every screen — tickets 06/07 get the whole mechanic for free and only write their row/table editors.
- **The Settings screen** (`internal/tui/settings.go`): four rows — Report Rate (cycles the Model's offered set), key delay, sleep, Fn switch — with a row cursor (↑/↓) and value editors (←/→); `*` marks every row that differs from the Device (the same truth the `pending:` line states). **Value domains came from evidence, not guessing** (spec Further Notes, "resolved by evidence"): the vendor bundle's own settings UI (`decoded/layout-classic-DSv6_q0d.js`) proves `keyDelay` is a level 1..5 (its `keyDelayList`, default 3), `sleepTime` is minutes 0..30 with 0 = never (its slider `min:1 max:30`, marks 1/10/20/30; sleep-off writes 0), `fnSwitch` is a 0/1 switch the app round-trips with no UI at all, and the NUT87's `reportRateList` is `[1000,4000,8000]` Hz → 1K/4K/8K. Recorded in `docs/protocol.md` §4/§6.6; `protocol.KeyDelayMin/Max`, `protocol.SleepMinutesMax` and `device.Model.ReportRates` (the seed of the CONTEXT.md "capability set": NUT87 = 1K/4K/8K) are the code homes. Editors clamp inside the domains; out-of-domain reads are shown as read, never rewritten.
- **Apply is the write path of ticket 04, generalized** (`internal/tui/write.go`): `a` with nothing pending says so and writes nothing; a read-only Device refuses with the same reason a refused load gives. Otherwise the session's FIRST apply runs the same gate as a load — fresh checked read (ADR-0003's check half), then the golden-read prompt with the same `device.GoldenPrompt` wording (`y`/`n`/`esc`) — and later applies skip the gate (the session's FIRST write is the gated one). `writeRequest` carries a `writeKind` whose phrasings (`load`/`apply`, `State File`/`your edits`) keep every gate/status sentence in one place; `device.ApplyChangesVerified` writes **only the blocks the edits changed** (`device.ApplyChanges`: never an untouched block, never a stale field) and proves it by read-back (spec user story 22). The wire encoding is pinned by test: applying 1K/4K/8K sends `SET_GAME_MODE` with reportRate `3/5/6` and nothing else, and the read-back verifies as set.
- **Rebase (the fix the review found):** the gate's fresh read replaces the Device's truth, so the edit buffer AND the payload of the write waiting at the gate are three-way merged onto it (`device.Rebase(base, fresh, edited)`: edited fields keep the user's values, untouched fields follow the Device). Without it an apply could silently write stale copies of fields the user never touched — exactly what "unsaved changes are never silently written" forbids. Pinned at the wire (`TestApplyWritesEditsOntoTheFreshestState`) and as a domain-function test (`TestRebaseKeepsEditsAndFollowsTheDevice`, same precedent as `RunChecks`/`Identify` tests).
- **Failed verification keeps the edits** (`TestApplyReadBackMismatchKeepsEditsPending`): the read-back is the truth on screen, the diff is shown (`(your edits → Device)`), and the edits stay pending (rebased onto the read-back) so nothing is lost silently — `r` drops them. A verified apply clears the buffer; a load rebases it (a load over pending edits is refused first: `refusing to load: N pending change(s) — apply or revert it first`).
- **Testing (both agreed seams):** `internal/tui/settings_test.go` drives whole sessions with key messages against the fake Device and asserts golden frames (the Settings screen, the four-row edit frame, the gate frame for an apply) plus wire/file assertions (only `SET_GAME_MODE` goes out of an apply, its payload bytes, no wire for edit/`r`/refusals, the golden file only on `y`). The full suite is green; `internal/cli` passes unchanged (the load write path's goldens are byte-identical).

**Code review (two-axis, post-implementation):** fixed the Spec finding (the stale-until-rebase write payload above) and the Standards findings (the `writeKind` phrasing switches → one wording type with `verb`/`action`/`sentLabel`/`wholeState`; duplicated status/gate-skip code → `writeStatus` + `writeOrGate`; `writeRequest.do()` renamed away). **Suppressed findings (deliberate):** `r` reverts from the Device's state as last read, without a wire round-trip ("the Device's actual state" vs an edit snapshot — external drift is ticket 08's watch/reset territory, and every apply refreshes truth from the read-back anyway); a verified apply shows its proof as the status sentence, not an empty `0 difference(s)` block (same as the load path since ticket 03); the quit-`q`-twice guard and the load-refused-while-pending rule extend "never silently lost" past the letter of "when switching screens" (a `q` or a load would otherwise drop edits silently — the guard is 3 lines); the save note (`N pending change not saved (the file snapshots the Device)`) because a State File is the Device's snapshot (CONTEXT.md) and the difference must not be a surprise; the `have, want State` parameter pair of `ApplyChanges` (it is the merge's shape); `tui.go` absorbing the shell's five small changes (it IS the shell).

**Follow-ups (not this ticket):** the Keys and Lighting editors (tickets 06/07) plug into `edit.go` and inherit apply/revert/gate/pending; a richer settings editor (e.g. sleep as a marked slider like the vendor's) is polish; `systemMode`/`powerMode` semantics stay open in `docs/protocol.md` §6.6.
